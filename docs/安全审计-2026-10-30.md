3. **中期**：接入云端用户体系，按 uid 配额，彻底废弃 sharecode 作为鉴权手段（它天生只能当"混淆"）。

### A2 · 限流在线上完全不生效

**实证**

```bash
# 破缓存连续 40 次（每次带随机参数，逐次确认 Eo-Cache-Status: MISS，即都回源到应用）
for i in $(seq 1 40); do curl -s -o /dev/null -w "%{http_code}\n" \
  ".../api/health?sharecode=...&cb=$RANDOM$i"; done | sort | uniq -c
#  40 x 200      ← 期望在 31 次后出现 429，实际 0 次
```

另测：32 次请求每次伪造不同 `X-Forwarded-For`，同样 32/32 返回 200。

**根因（`server.js:75-84`）**

```js
const rateBuckets = new Map();                    // 进程内内存
const clientIp = String(req.headers['x-forwarded-for'] || req.socket.remoteAddress || 'unknown')
  .split(',')[0].trim();                          // 取 XFF 第一段 = 客户端可伪造
```

两个致命点叠加：
1. **信任 `X-Forwarded-For` 首段**。该头由客户端发送，取第一段等于让攻击者自报 IP，一个头就换一个桶。
2. **进程内 Map**。线上经 CDN 网关回源，若存在多实例/多回源出口，桶会被天然打散；进程重启也会清零。

**后果**：`GLOBAL_CONCURRENCY=8` 的闸门只能防"同时"，防不住"持续高频"；攻击者可用单线程脚本连续触发 `/api/analyze`，把 LLM 配额与 CPU 全部吃满，页面本身随之不可用。

**修复建议**

```js
// 1) 只在可信代理后才读 XFF，且取最后一跳（离你最近的那一跳由网关写入）
function clientIp(req, trustedProxy) {
  if (trustedProxy) {
    const xff = String(req.headers['x-forwarded-for'] || '');
    const parts = xff.split(',').map((s) => s.trim()).filter(Boolean);
    if (parts.length) return parts[parts.length - 1];
  }
  return req.socket.remoteAddress || 'unknown';
}

// 2) 计数放共享存储（多实例一致），无 Redis 时退化为「网关/WAF 限流 + 本地上限」双层
//    最小可用方案：给每个 sharecode 令牌一个总配额（如 500 次/天），用完即停
```

优先级：**先把限流放到 CDN 网关/WAF 层**（对 `/api/*` 做每 IP 每分钟 30 次），代码层作为第二道兜底。

## 三、P1 详细分析

### B1 · CORS 通配

线上每个响应都带 `Access-Control-Allow-Origin: *`（`server.js:661`，`.env` 中 `ALLOWED_ORIGIN=` 为空）。

后果：配合已扩散的 sharecode，**任意网站都能在访客浏览器里直接调用接口并读取返回**，可用于免费白嫖你的模型能力（把页面当成别人的 API 后端），也可用于跨域探测。

```js
// 修复：生产必须收拢，并加 Vary
const origin = String(req.headers.origin || '');
const allow = ALLOWED_ORIGIN && origin === ALLOWED_ORIGIN ? origin : '';
if (allow) res.setHeader('Access-Control-Allow-Origin', allow);
res.setHeader('Vary', 'Origin');
```

顺带修一个隐性 bug：`Access-Control-Allow-Headers` 只写了 `Content-Type`，不含 `x-share-code`，所以前端走请求头传 code 的跨域预检会失败、静默退回 query 传参——这也让 code 更容易进日志和 Referer。

### B2 · 安全响应头缺失

实测线上响应头只有网关自带的 CORS 与 `X-Request-Id`，**以下全部缺失**：

| 头 | 缺失后果 |
|---|---|
| `Content-Security-Policy` | 任何一处 innerHTML 漏转义即全站脚本执行（`app.js` 有 109 处 innerHTML 赋值） |
| `X-Content-Type-Options: nosniff` | 静态资源 MIME 嗅探 |
| `X-Frame-Options` / `frame-ancestors` | 可被 iframe 嵌套用于点击劫持（评分、删除、提交） |
| `Referrer-Policy` | **sharecode 会随 Referer 泄露给任何第三方资源**，这条对本项目伤害最大 |
| `Permissions-Policy` | 摄像头/麦克风权限可被上层页面借用 |

```js
// server.js 顶部统一注入
res.setHeader('X-Content-Type-Options', 'nosniff');
res.setHeader('X-Frame-Options', 'DENY');
res.setHeader('Referrer-Policy', 'strict-origin-when-cross-origin');
res.setHeader('Permissions-Policy', 'camera=(self), microphone=(self), geolocation=()');
res.setHeader('Content-Security-Policy',
  "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; " +
  "img-src 'self' data: blob:; connect-src 'self' https://jiangtai-survival.app.workbuddy.host; " +
  "frame-ancestors 'none'; base-uri 'none'; object-src 'none'");
```

上线前注意：若页面里有内联 `<script>` 或内联 `onclick=`，需先外链化或加 nonce，否则会被 CSP 直接拦死（`workbench.html` 有 4 处 innerHTML、多处内联样式事件，需先自查）。

### B3 · 云会话 cookie 的 CSRF 面

实测 `Set-Cookie: __wb_rsc=...; HttpOnly; Secure; SameSite=None`。

`SameSite=None` 意味着**跨站请求会带上这个会话 cookie**，而代码里没有任何 CSRF token。攻击者页面可对云端接口发起跨站写请求（写排行榜、发树洞、删复盘记录），是否成功取决于云端 RLS 的校验强度（目前依赖 `owner_id = auth.uid()` 兜底，能挡住越权读别人的数据，但挡不住"以你的名义写"）。

建议：写操作前带一次性 token（云端返回后回传），或把 cookie 改为 `SameSite=Lax`（本项目没有跨站嵌入需求，`Lax` 够用）。

## 四、P2 详细分析

**C1 · 上传接口**
`handleUpload` 只按字节数截断（50MB），没有 MIME / magic bytes 白名单；`parseMultipart` 是手写的；`readRawBody` 会把整个文件读进内存，`GLOBAL_CONCURRENCY=8` 时理论峰值 ~400MB，配合无效限流可被用于内存打爆。`heavyQueue` 数组也无长度上限。
建议：读前 12 字节校验 `ID3` / `RIFF` / `ftyp` / `OggS` / `fLaC` 魔数，不匹配直接 415；把 `MAX_UPLOAD_MB` 降到 25；`heavyQueue.length > 64` 直接 503。

**C2 · 错误信息外泄**
`server.js` 六处 `sendJson(500, { error: e.message })`；而 `lib/deepseek.js:116` 抛出的 message 是 `AI_HTTP_429: <上游响应体前 200 字>`。这会把上游报错原文（含模型名、请求 ID、有时含部分请求内容）回给客户端。
建议：对外统一 `{ error: '服务暂时不可用，请稍后重试' }` + 一个可追踪的 `traceId`，详细错误只进服务端日志。

**C3 · 健康接口信息量偏大**
`/api/health` 返回 `aiMode / model / baseUrl / hasKey`。`baseUrl` 直接告诉攻击者上游供应商（DeepSeek）与接口形态，便于针对性刷。建议只保留 `{ ok, mode: 'live'|'demo' }`。

**C4 · 数据流向与合规**
试讲音视频 → 服务器转写 → 文本进 DeepSeek。若涉及真实课堂录音（含未成年人声音），需在页面上明示"数据将发送至第三方模型用于分析"并给出删除入口。当前 `uploads/` 在 `finally` 里 unlink（本地已验证为空），但进程被强杀时会有残留；建议启动时清理 `uploads/` 下超过 1 小时的文件。

**C5 · 细节**
`OPTIONS` 走 `sendJson(res, 204, {})`，204 不应带 body（部分客户端会报协议错）。`serveStatic` 的 `decodeURIComponent` 遇到畸形 `%` 会抛错落到 500，规范上应是 400。
